# Virtual Families 1: divide-by-zero audit

Every integer division (`div`, `idiv`, every operand form) in the code of the vanilla `Virtual Families.exe`
(1.01.00) that the game can run, with where its divisor comes from and whether it can be 0 in play.

## Method

* **Which code can run.** Recursive descent from the entry point, the same method as the research `reach.py`:
  direct calls, jumps and branches, jump tables, code addresses the code takes (`push` / `mov` of a code address),
  virtual methods of every class whose vtable reachable code stores (a class that is made), and the C runtime's
  static-initializer tables (`_initterm` 0x4B2464..0x4B2540, 0x4B2544..0x4B2560).
  `tests/test_divide_by_zero_audit.py` repeats that walk on the vanilla exe and checks that the divisions it finds
  are exactly the sites in the table below, so a missed or extra site fails the test.
* **What it finds.** 211 divisions: 156 in the game's own code
  (below 0x497848) and 55 in the statically linked C runtime. None is
  skipped: the C runtime's divisions are listed too, each with its constant or its check.
* **64-bit division helpers.** `_aulldiv` 0x49E330, `_alldiv` 0x49EC80, `_aullrem` 0x49ED40 and `_aulldvrm` 0x4A8650
  are the only ones (no `_allrem`). Every call to them is in the C runtime's time and `printf` code, with constant
  divisors; no game code calls them.
* **Random ranges.** GetRandom 0x403650 (`rand() % n`) divides only when n is 1..0x7FFF (0x403658..0x403660);
  any other n takes 0x403671..0x4036C5, which has no integer division and returns 0 for n <= 0. So none of its
  5,085 callers can make it divide by 0 (one passes 0, 0x47A1EA, and the rain's respawn passes -561, 0x491DF0:
  both get 0). Proved by emulation in `tests/test_divide_by_zero_audit.py`.
* **Classes.** SAFE-CONSTANT: the divisor is a constant (or always one of a few constants). GUARDED: the code
  checks the divisor (or what it is made from) first; the check is named. UNREACHABLE-ZERO: the divisor comes from
  game values, but it cannot be 0 in play; the proof is given. REACHABLE-CRASH: emulated to fault, and a real
  family can reach it.
* **Evidence.** "emulated" names the test that runs the game's own code in Unicorn; "read" means proved from the
  disassembly (addresses given).

## Summary

| Class | Sites |
|---|---|
| SAFE-CONSTANT | 61 |
| GUARDED | 114 |
| UNREACHABLE-ZERO | 35 |
| REACHABLE-CRASH | 1 |
| Total | 211 |

The only REACHABLE-CRASH site is the bank chart's 0x415392; Fix Vanilla Game Bugs fixes it (`InstallBankChartFix` in `native/vf1fun/vf1fun.cpp`, proved by `tests/test_bank_chart_fix.py`). No other site needs a fix.

## Weather

Every weather path, checked for a divide by zero, a bad index and a missing picture (owner, 2026-11-01). In
Virtual Villagers 3-5 the same LDW-style rain crashed: a raindrop is drawn as a line from its point to its
previous point, the line drawer divides by the longer side, and a drop drawn before its previous point was ever set
was a zero-length line. **Virtual Families 1 has the same latent shape but cannot reach it: no weather path can
crash, and Fix Vanilla Game Bugs needs no weather fix.**

* **Weathers.** Four kinds, [0x8352A4] +0: 0 clear, 1 sunny (sunbeams), 2 rain, 3 storm (rain and lightning).
  There is no snow, no lightning bolt (the storm's lightning is a full-screen flash) and no cloud. The only line
  drawn in the game is a raindrop: 0x404200's only caller is 0x4082B0 (0x4082DD), whose only caller is the rain
  draw (0x491D9A).
* **No division of their own.** The weather code (0x4908B0..0x4928E0) has no `div` / `idiv`. Every integer
  division reachable from the weather's entry points (its draw, update, changes, reset, the rain bottle, the lamps,
  the pictures it loads, the effects it adds and draws; a call-graph walk) is a row of the table above, none a
  crash: GetRandom 0x403668, the line drawer 0x4043A8 / 0x4043B2, the blitter's averages 0x405177.. / 0x406270..,
  the cell lookups 0x408953 / 0x408962 / 0x408E23 / 0x408E32 / 0x40B135 / 0x40B142, the picture grids 0x40AD51..
  / 0x40AE68 / 0x40AE77 / 0x40B02A.., the effect draw 0x421A6E / 0x421A8B, the archive read 0x40F8EE / 0x40F920
  and 0x411C8B (pictures loaded on first use), and C runtime time code with constant divisors.
* **x87 divisions** (the strength and haze ramps, the sunbeams, the darkness, sunrise and sunset) never fault: the
  x87 runs with its exceptions masked (0x27F), and every `fldcw` in the game's own code only adds the rounding bits
  0xC00 to the control word it read (0x4036B4, 0x403744, 0x403BC6, 0x412E90, 0x42238E, 0x491A3E, ...) or puts
  that word back. A 0 / 0 gives a NaN, followed below.
* **Emulated** by `tests/test_weather_crash_audit.py`: the game's own code in Unicorn (`tests/house_emu.py`), from
  the zeroed objects and their constructors through the reset, changes, updates and draws below, down to the real
  line drawer 0x404200 on a real 800 x 600 screen and the real blitter 0x404C30. Any CPU fault stops the run and
  fails the test, and every call must return. Stood in for: GetRandom (the game's answers: 0 for n <= 0, else a
  value below n; worst cases "always 0" and "always n - 1", and seeded runs), the clock CGameTime::Seconds,
  SDL_GetTicks, the sounds, the villagers' rain notice 0x48AE40, the daytime test 0x491630 and the next-weather
  pick 0x492230 (both read the C runtime's clock), SDL_MapRGB(A).
